# Distributed application design interviews

Use this sequence when a feature spans a desktop/client and one or more workspace hosts. Ask only questions whose prerequisites have been settled; this is a dependency guide, not a questionnaire to dump at once.

1. **Establish the actual application boundary.** Inspect the relevant client and backend repositories and their instructions. Identify who owns presentation, processes, and structural state. Verify where services run without modifying the live installation. Do not infer graphical embedding support from a project name or from JavaScript support; native UI frameworks may have neither a DOM nor a browser engine.
2. **Separate execution from presentation.** Ask where the process executes, where its output is displayed, which host supplies network requests and `localhost`, and where credentials and files live. Contrast actual remote execution with local execution plus port forwarding using a concrete two-machine scenario.
3. **Define identity and UI hierarchy.** Resolve whether state belongs to a workspace, host, user, or client. Distinguish outer application tabs, inner content tabs, panes, and independent sessions; these determine ownership and persistence rather than merely visual styling.
4. **Specify lifetime as separate events.** Cover switching away, hiding a container, closing a content tab, quitting the client, losing connectivity, restarting the backend, process crashes, and host reboot. Distinguish preserving a live process from restoring saved URLs or metadata; restoration cannot generally recover volatile page state. Treat process survival across backend restarts as a requirement to verify, not an automatic consequence of backend ownership.
5. **Resolve concurrency explicitly.** Distinguish multiple viewers with one controller from exclusive attachment. Decide lock scope, stale-owner release, reconnect behavior, takeover policy, and which client controls viewport dimensions. A shared live page normally has one viewport, even if several clients view it.
6. **Trace files and privileges across hosts.** Define download location, explicit client transfers, upload staging, clipboard direction, permission prompts, and external URL handling. Separate profile/cookie isolation from OS isolation; profiles under the same account are not independent security boundaries. Keep untrusted content separate from privileged application/mod bridges.
7. **Turn engine and tooling requirements into technical prerequisites.** Ask whether an exact engine family, remote inspection tools, native display protocols, or headless execution are required. Inspect existing integration points before promising feasibility. Distinguish source-grounded plausibility from an exercised prototype; remote rendering and input transport need validation beyond tab-model support.
8. **Close on observable acceptance scenarios.** Include reconnecting from a sleeping laptop, a competing client, access to a host-local development server, independent workspace logins, and recovery after a browser crash. Preserve unanswered choices as open decisions rather than silently assigning defaults.

Keep browser automation separate from human browsing. A remote debugging transport needed for human DevTools does not itself grant terminal agents permission to inspect or control logged-in pages; define that authorization boundary explicitly.
